# LiveLingo 2.0 · 整理效果与窗口缩放设计

状态：**整理已用真实模型验证；窗口缩放已实施，真机（macOS / Windows）未验证**。相关：[语音识别设计](./2026-10-29-voice-dictation-design.md)、[Composer 设计](./2026-10-31-livelingo-composer-design.md)、[偏好设计](./2026-11-01-preferences-design.md)。

## 1. 整理几乎没改动原话：原因

用户截图里的 19 个碎句，整理后基本一样。用真实模型（Qwen3.5 4B）按产品原来的方式复现：19 句中 11 句有变化，但全是**标点和空格**；碎句没合并，“准确率很高。准确率不是很高”这样的重复没去掉，同音错字没改。还有一个副作用：模型去掉了句末标点，拼起来成了“位置比如”“因为 VS Code”这样的连句。

根因是**粒度**，不是提示词保守：

1. 识别器按停顿切话（硬停顿 800 ms），断出的单位是半句话（“因为。”“…不是。”）。一句话单独看没有信息，模型只能做标点和口头语。
2. 同音错字、重复、半句要靠**上下文**才能判断。原来只给前两句已整理的文字，且目标永远是一句。
3. 保真门禁是按“一句进一句出”设计的：跨句的重复、改写会被当成“无故删除”而拒绝，所以即使放大粒度，门禁也要一起改。

同一个模型，把整段交给它，效果明显不同（同一份截图原文）：

> 我周末写了一个工具，可以在任何位置，比如 Slack 聊天、Teams 聊天，甚至 VS Code 和 Cursor 的聊天框里，把语音输入实时接入进来。因为 VS Code 和 Cursor 对于中文的语音识别准确率不是很高，所以我写了一个 POC 验证了一下，然后做出了这个工具。……你觉得怎么样？

## 2. 设计：按段整理

**单位从“句”改成“段”。** 听写产生的单位是一段话（几句），整理、翻译、编辑、重试仍然是“每个单位一份结果”，界面的行模型不变，只是每行更长。

### 2.1 成段（`DictationSession`）

识别稳定下来的句子先攒在“当前段”里，满足任一条件成为一个单位：

| 条件 | 值 | 理由 |
|---|---|---|
| 说话人停了 `PassagePauseMs` | 2000 ms | 尽早提供逐段预览；不以这条边界作为最终润色的边界 |
| 当前段达到 `PassageMaxChars`，在句末成段 | 200 字 | 长篇口述不会一直等到停顿；整理一段约 4 s |
| 停止听写 | — | 刷出剩余内容 |

- 停顿用**音频样本位置**判断，不用墙上时钟。“这一段在这里结束”记在最后一个片段上，所以二遍识别还没回来时，顺序和边界也是对的。
- 攒着的内容和未成句的尾部都在 `Draft.Pending` 里实时显示，成段那一刻同一次更新里变成单位。
- 打字、粘贴的文本仍按句拆分，不受影响。

### 2.2 整理（`LlmTextCleaner`、`CleanupScheduler`）

- 提示词改为“整理一段口述”：接上被切碎的半句、去口头语、重复和放弃的半句、自我纠正只留纠正后的、依据上下文改正同音错字和术语（词表优先）、**英文和术语一律保留**。保留“不新增事实、不改否定条件范围、不改数字、不回答问题、不删提问和结论”。
- 去掉“尾句 holdback”：一段是在长停顿后才产生的，不必再等。录音中最后一段的 `Continues` 为真（麦克风还开着，说话人可能继续）；这一点影响模型行为，见 §4。
- **门禁失败时降级为逐句**：整段没过门禁，就把这一段按句再整理一遍，每句各自过门禁；通过的句子用整理结果，没通过的句子保留原话。只有**一句都没通过**才整段保留原话并显示原因。一句坏话不会让整段失去整理。多行文本（整篇文档）不拆。

### 2.3 保真门禁（`FidelityGate`）

门禁是启发式检查，不是语义等价的证明，可能误拒或漏检。真实口述里常见的误拒是**删掉了虚词**：“选择股票的话”“那么”“他们的这个工作”被当成“无故删除”，整段退回原话。现在允许四类可解释的删除：

1. **口语虚词**：“的话、那么、然后、其实、这个、一下、呢、呀、吧、嘛……”整段被删算作语气词。
2. **轻微删减**：删掉不超过 3 个字、不含否定的零碎字（“他们的”“这边”），累计不超过原文的 8 %（至少 4 个字）。更大的删除仍拒绝，几处零碎删减加起来也会超预算。
3. **复述**：被删掉的字，其相邻字对大部分（≥ 60 %）仍出现在整理后的文本里，说明说话人只是把同一句话说了第二遍（“准确率很高。准确率不是很高”）。
4. **说出来又改掉的英文词**：词后 12 字内有“不对 / 说错了 / 我是说 / 更正”（“click 事件，不对，是 command 属性”）。“不是”“改成”也出现在普通陈述里，所以不算。

**否定字**（不、没、别、无、非、未、否）的删除一律不豁免，包括单独一个“不”：丢了“不”会变成反义。其余规则（数字丢失 / 新增、术语丢失 / 不在词表、括号、长度比例、新增字数）不变。

### 2.4 编辑原文时（`Draft.SyncSource`）

用户改原文时，源文本被重新拆成句子。**一个单位可以对应一串句子**：这串句子在源文本里原样不变（且同一行内）时，这个单位和它的结果继续保留；被改过的段退回逐句。这样改一个字不会让别的段重新整理。

### 2.5 停止后的全文润色（`PolishScheduler`）

说话时每段单独整理，只能在段内接话；用户在想事情时的停顿会把一句话切在段与段之间（“我想了解的是。”｜“行业大牛是怎么……”）。实测（用户 12 段口述）：逐段整理的结果读起来仍是 12 个孤立的短句，而**整篇一次交给模型**就得到连贯的段落。所以**停止录音后**，对整篇口述再做一遍：

- **停止即触发，不等待逐段任务排队完成**。取消尚在运行的逐段整理；`Draft.Recording` 从真变假时同步设置 `Polishing`，UI 通知尚未送达时，写入也已经被阻止。
- 先为完整原文生成主题/术语摘要，再润色。摘要只读，原文始终随润色请求提交，不能拿摘要代替原文。超出摘要输入预算的长文分块摘要后再合并，避免只读取前 2500 字。
- 每次润色最多 800 字原文；短口述整体提交，长口述按连续单位分组，所有组读取全文摘要，并携带前文约 300 字。最终润色使用独立的 `IDictationPolisher`，逐段预览仍使用 `ITextCleaner`；二者共享同一个整理角色、路由和本地模型。
- 整组结果过**同一道保真门禁**（对着原文）。通过：这一组段合并成**一个单位**，原文是它们拼起来的原文，整理结果是润色后的文本；用户仍可“用原话”回到原文。
- **不再递归拆分重试**。实测重复/噪声长文会因反复拒绝而串行调用多次模型，等待超过一分钟。默认要求的结果不通过检查时保留逐段结果；只有自定义要求无效时，额外重试一次默认要求。截断、不完整输出不得作为成功结果。
- **写入要等润色做完**：显示“正在润色全文… 此时写入会等润色完成”；按回车排队，结果完成且可用后才写入。录音中右侧标注“实时整理预览 · 停止后润色全文”，不把预览冒充最终结果；复制和导出同样遵循准备状态。关闭按钮只保留草稿，不会写入半成品。
- 单段录音也执行最终润色；重新录音后结合新增内容再次处理。旧请求受录音版本、原文版本、取消令牌约束，不能回写到新录音、源文本编辑或人工结果编辑中。
- 不覆盖人工编辑过的整理稿或译文，也不合并带排版/时间轴的单位。失败原因写不含原文的诊断日志；最终没有采用全文结果时，界面明确提示“已保留逐段结果”，不显示成功式提示。

实验不是 M2/16 GB 产品验收：本机 Qwen3.5 4B，252 字样本连贯成一段；包含两次推理及冷启动时约 10 s。1030 字重复/噪声压力样本，取消递归后最终阶段从约 79 s 降到约 16 s，但该样本最终结果被门禁拒绝，仍需逐段结果，不应声称润色质量已解决。摘要额外增加延迟，实测不总改善短文质量；这里遵循“先摘要再润色”的产品选择，保留明确的等待状态。

### 2.7 可编辑的全文润色要求

- **设置 → 语音与翻译 → 全文润色要求**：展示当前默认要求供直接编辑，失焦保存，支持一键恢复默认。只影响最终全文润色，不影响实时识别、逐段预览、翻译或隐私路由；下次唤起生效。
- 可编辑的是风格要求；输入格式、不得新增事实、保留提问/数字/条件等约束在固定提示词中，输出仍过保真检查。模型和检查均有局限，不能承诺任意自定义要求都能被安全执行。
- `PolishStyle` 是校验和默认值的唯一来源：10–1500 字符，允许正常换行/制表符，不允许控制字符。交互中无效的编辑显示错误、不覆盖最后有效配置；空白和“恢复默认”存为空字符串，以后内置默认升级可自动生效。
- 设置缺失、空白、过短、过长、损坏时解析为默认要求；整个 JSON 损坏沿用设置服务的默认恢复。格式合法但模型输出不可用的自定义要求，重试默认要求，成功后明确提示已切换默认；默认仍失败则保留预览并提示。
- 保留原文与“用原话”入口。摘要不写入结果，也不作为新的术语或事实来源。

### 2.6 逐段整理的两个失败模式

1. **模型把只读前文抄进输出**（前文加大到 300 字后更常见）：抄了前文，输出就比目标长得多，被判“过长”；更糟的是超过为目标预留的输出上限，服务以 `finish=length` 报错，这一行变成红色错误，必须手动重试或手动输入，还挡住写入。现在：输出上限给前文留出空间；输出开头与前文结尾相同的部分（按字母数字比较，不管标点）被去掉；**回答被截断不再是错误**，和任何被拒绝的整理一样保留原话、可以写入（提示“模型的回答被截断”）。
2. 逐段整理仍可能被门禁拒绝（短碎片尤其容易被抄前文）；这只是说话时的预览，停止后的全文润色会重新处理。

## 3. 窗口缩放

### 3.1 目标与取舍

用户内容多时，需要更大的窗口来预览。要求：直观、不误触、有快捷键、不超出屏幕、不改变已有的“窗口跟内容走”的默认体验。

| 决定 | 备选 | 取舍 |
|---|---|---|
| 右边、下边、右下角可拖 | 四边四角 | 窗口默认贴着目标输入框的下沿，向上长；只用右 / 下，窗口左上角不动，页面里的指针位置**就是**想要的大小，不用屏幕坐标（WebKit 的屏幕坐标不可靠）。想往上、往左放大，先拖标题移动窗口，或用放大 |
| 手柄在面板内侧，细条 5 px，角 16 px | 画在阴影边距里 | 透明窗口的完全透明区域在 macOS 上会把点击穿给后面的窗口，边距里的手柄收不到事件 |
| 光标提示，不画抓手 | 右下角画抓手 | 面板圆角 22 px，抓手要么被圆角切掉，要么压到“写入”按钮 |
| **标题栏右上角的图标按钮**（放大 / 还原，在关闭按钮左边）、`⌘E` / `Ctrl+E`、双击边缘 | 放在“更多”菜单里 | 放大是高频、直接的窗口操作，和关闭按钮同一排；不放进菜单。图标随状态切换（放大 ↔ 还原），提示里带快捷键。放大后：宽 1100、高为工作区高度，居中 |
| 窗口尺寸由 C# 决定，页面只报“想要多大” | 页面自己改窗口 | 和移动一致：页面只说意图（`resize`、`zoom`），宿主按屏幕工作区限制 |
| 拖动后高度固定，面板铺满窗口；并排布局下左右两栏各自撑满高度、各自滚动 | 整个面板一起滚 | 才能“预览更多内容”；有空间时不出现滚动条；还原后恢复内容高度 |
| 默认的面板上限按屏幕工作区高度的 70 %（原来固定 470 px），文本区上限随之放大 | 固定像素 | 大屏上不再“屏幕没占满滚动条就出现”；小屏仍受工作区限制 |
| **不记住大小**，每次唤出从紧凑开始 | 按应用记住 | 偏好设计已定：窗口位置和大小是单次草稿的事；多数唤出是短输入，紧凑最快。若常在某个应用里用大窗口，可以后续加到“按应用记住”（见 §5） |

### 3.2 流程

1. 页面在 `.rz` 手柄上按下，捕获指针；移动时记下 `起始窗口大小 + 指针位移`，每帧最多发一次 `resize{width,height}`（不变的一维为 `null`），松开时发最后一次。
2. 宿主 `ComposerWindow.OnResize`：把窗口**钉在当前位置**（和被拖动过一样），按 `ComposerPlacement.Resize` 限制到“最小可用大小 ~ 从左上角到工作区右 / 下边缘”，设置窗口宽高，并通知页面 `frame{fixedHeight:true}`。
3. 页面收到 `frame`，给 `<html>` 加 `fixed-h`：面板高度 = 窗口高度，文本框和实时区的高度上限放宽。
4. `zoom`：未调整过 → 放大；调整过或已放大 → 恢复（取消钉住，宽度回到窄 / 宽布局的默认，高度回到内容高度，按目标窗口重新定位）。

窗口宽度原来由“窄 / 宽屏对照”决定；现在用户拖过宽度后以用户的为准，再切换宽屏对照不覆盖。最小宽度：窄布局 520、并排布局 760（CSS 像素，不含阴影边距）。

### 3.3 边界

- 不会超出屏幕：大小被限制在工作区内；窗口位置只在拖标题后才会被夹回屏幕内。
- 多显示器：限制按窗口所在屏幕的工作区和缩放计算。
- 钉住后窗口不再因内容高度变化而移动；放大或还原是唯一的复位方式（或下次唤出）。

### 3.4 清空与模型提示

- 原文栏右上角常驻“清空”文字按钮，复用 `NewDraftCommand` 和 `Cmd/Ctrl+N`，不新建第二套清空逻辑。它停止录音、清空当前原文/整理稿/译文/时间轴，取消待写入内容，保留目标、输出选择、偏好和历史列表。清空后焦点回原文框。
- 启动中的录音必须等启动/停止完成后再重置；清空期间显示“正在清空”，禁止重新开麦、写入或导入。停止操作共享进行中的任务。原生识别超时后线程可能仍在运行，因此识别会话捕获 `Draft.Epoch`，所有写操作拒绝旧代次，不能只依赖 UI 的取消标志。晚到的提交、转录和识别结果都不能写入新草稿。
- 模型提示是实际运行事实，不从设置值推断。`ModelUsage` 在语音实例创建、本地模型租约获取和云端服务响应边界报告；预热不冒充使用。录音开始、有效模型变化时提示约 5 秒，不长期占用正文空间；点击或悬停“本地/云端”可再次查看详情。
- 待准备模型和已实际加载模型分开；切换时显示新请求与上次实际模型。云端只回显请求别名时明确标注“服务端尚未回传模型名”，不把部署别名当成确认的后端模型。
- 模型职责分开：X-ASR 480 ms 实时识别 + Qwen3-ASR 0.6B 二遍校正；Qwen3.5 4B 整理/摘要/润色；Hy-MT2 1.8B/7B 翻译。“快速/质量”只影响翻译，不更换语音识别器。
- 查到两个切换问题：旧模型尚有请求时直接停止服务；打开的 Composer 保留旧模型需求和译文缓存。现在等待旧租约释放再切换，并刷新当前 Composer 的需求及非人工译文；源文本与人工译文保留。
- 已用真实本地服务执行 1.8B → 7B → 1.8B，三次响应分别报告对应 GGUF 文件，不是只核对配置枚举。Windows 原生交互仍需真机验收。

## 4. 验证与已知限制

已验证：

- 真实模型对截图原文、6 个合成段落、8 个语料场景和一段带长停顿的合成语音（macOS `say`）走完整个管线：碎句被接起来，重复被去掉，门禁通过；门禁拒绝的都是确实应该拒绝的（模型把“五零三”改成了“503”、括号不成对、删了否定词）。
- 单元测试：门禁新规则（含否定不豁免）、成段（停顿 / 长度 / 二遍识别未回时的边界）、逐句降级、`SyncSource` 的段保留、缩放的限制计算、意图校验；浏览器测试（WebKit + Chromium）：三个手柄的拖动、双击、`⌘E`、`frame` 后面板铺满窗口。

已知限制：

- **模型对 `Continues` 敏感**：同一段话，`后文：说话已经结束` 比 `说话人还在继续` 更容易被大幅压缩（会被门禁拒绝）。录音中最后一段按“还在继续”处理，停止后才是“结束”。
- 模型不能纠正识别器完全听错的词（“聊天狂”“pop”），更不会凭空补出术语；这些靠识别质量和词表。
- 窗口拖拽缩放的手感（延迟、光标）、macOS 透明窗口的事件命中、Windows 的 DPI 缩放都**没有真机验证**，需要在 Mac 和 Windows 上各过一遍。
- 编辑过的段退回逐句整理，质量回到旧水平。
- 前文是上一些段已整理好的文字，约 300 字（至少带上一整段），只读：新一段能参考它，但不能回改它。上一段末尾若是没说完的半句、下一段才补完，说话时两段不会被重整到一起；**停止后的全文润色（§2.5）**补这个缺口：润色期间状态是“正在整理…”，写入排队等它，结果出来时对应的行合并成一行。

## 5. 开放问题

1. 大小要不要按应用记住（在 Slack 里紧凑，在编辑器里用大窗口）？成本很小：`AppChoice` 加一个可选的“放大”标记。
2. `PassagePauseMs`（2000 ms）和 `PassageMaxChars`（200 字）仍需真人口述验证；实时预览不再承担最终连贯性的承诺。
3. 门禁对“整段保留原话”的提示文字目前沿用 “已保留原话”；逐句降级后部分保留的情况不提示。
