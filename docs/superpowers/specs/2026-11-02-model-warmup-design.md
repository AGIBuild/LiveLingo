# LiveLingo 2.0 · 模型预热设计：什么时候加载，加载多久，留多久

状态：**已实施（真机未验证）**。相关：[Composer 设计](./2026-10-31-livelingo-composer-design.md) §4（按需驻留）、[语音识别设计](./2026-10-29-voice-dictation-design.md)。

## 1. 问题与数据

每次开始听写都要重新加载语音模型，并在停止时丢掉；整理与翻译模型在第一次请求时才启动。用户第一次按下麦克风要等几秒，第一句整理要等更久。

实测（Apple M3 Pro，磁盘缓存热 / 冷，非产品验证基线 M2 / 16 GB，绝对数偏乐观）：

| 模型 | 之前 | 现在（预热后） | 驻留内存 |
|---|---|---|---|
| 语音：X-ASR 流式 + Qwen3-ASR 二遍 + VAD | 每次听写 3.2 s（冷 5.1 s） | 并行预热 1.8–2.3 s；预热后开始听写 **4–15 ms** | 进程内存约 1.4 GB（卸载后回落到约 0.6 GB） |
| 整理：Qwen3.5 4B（llama-server） | 首句 10 s（冷盘）/ 约 2 s（热盘） | 预热约 1.4–2.4 s；预热后首句约 1.1 s | 另计（独立进程） |
| 翻译：Hy-MT2 1.8B | 首句 1.7 s | 预热约 1.1 s；预热后首句约 0.2 s | 另计 |

空闲卸载后进程内存从约 1.4 GB 回到约 0.6 GB（卸载后的基线含原生运行库的残留）。

## 2. 原则

1. **界面从不等模型**：浮窗瞬间出现；模型在后台准备；准备中看得见，按下麦克风也不报错，只是等到好为止。
2. **在用户“可能要用”的最早时刻加载，在“不太会用”时释放**：内存是有代价的（16 GB 基线），所以不是一律常驻。
3. **一个地方决定“何时”**（`ModelWarmup`），一个地方决定“留多久”（模型自己的空闲超时）。界面、视图模型不各自预热。
4. **预热只是优化，不是功能**：失败不打扰用户（记日志）；真正需要时由使用者再请求并报告错误。
5. **不违背隐私**：只加载本机已安装的模型；整理或翻译角色走云端时不加载本地模型。

## 3. 时机

| 时机 | 加载什么 | 理由 |
|---|---|---|
| 应用启动后 3 秒（设置“启动时准备语音模型”，默认开） | 语音模型 | 应用常随登录启动，用户还没唤起时就加载完；晚 3 秒让启动先完成（托盘、热键、窗口） |
| 语音模型刚下载完 | 语音模型 | 首次安装后的第一次按键也不用等（同样受上面的开关约束） |
| 唤起浮窗（每次） | 先语音模型（若已被卸载或未预载），再加载**起始输出**对应的模型（整理或翻译） | 唤起到开口之间通常有 1–3 秒，足够开始加载；先语音后整理，避免两个大加载抢 CPU 把语音拖慢 |
| 用户（或横幅）切换输出 | 新输出的模型 | 切到“翻译”意味着马上要翻译 |
| 不预热 | 云端角色的本地模型；未安装的模型；“原话”输出；关闭整理后的整理模型 | 用不到 |

**为什么不在启动时也加载整理和翻译模型**：它们合计约 3.7 GB（1.8B 档），且用户不一定用；唤起时才预热足够（预热 1–2 秒，用户在这期间说话也已有语音可用）。

## 4. 驻留与释放

- 语音：`ResidentModel<T>`（单一实现）——一次加载、被听写与录音导入**借用**、空闲 `CoreOptions.SpeechIdleTimeout`（默认 30 分钟，从最后一次使用或预热算起）后卸载；再次需要时重新加载。
- 整理 / 翻译：沿用 `LlamaServerHost` 的 10 分钟空闲卸载；预热只是“启动并立刻归还”。
- 热词（术语表）属于二遍识别模型的加载参数：术语表变了，只重载二遍模型（约 1.7 s），在下次唤起预热时完成。
- 借用期间不会卸载；同一模型同时借给两个不同的键是编程错误（听写与录音导入在界面层互斥）。

## 5. 体验

- 浮窗打开后若语音仍在加载：底部状态行（无文字时）显示“语音模型准备中，稍后可用…”，加载完即消失。
- 此时按下听写：状态变为“正在加载语音模型…”，加载完自动开始（沿用既有的“启动中再按一次取消”行为）。
- 设置 → 语音：“启动时准备语音模型”（默认开），说明里写明内存（约 1.5 GB）与 30 分钟释放；关闭后只在唤起时才开始加载。

## 6. 组件

| 组件 | 职责 |
|---|---|
| `ResidentModel<T>`（Core） | 单次加载、借用、空闲卸载、状态事件；不知道模型是什么 |
| `SherpaSpeechEngine`（Core） | 语音模型唯一的拥有者：听写会话工厂、录音导入、`ISpeechWarmup`；替代每次加载的 `SherpaDictationSessionFactory` 与 `SherpaAudioFileTranscriber` |
| `IInferenceWarmup` / `LlamaWarmup`（Core） | 启动某角色的本地服务；该角色走云端时什么也不做；每个角色用哪个模型只在 `InferenceModels` 里决定 |
| `ModelWarmup`（Desktop） | 唯一决定“何时”预热的地方（上表） |
| `IVoiceInput.IsPreparing` | 让视图模型知道“语音正在准备”，以显示状态 |

## 7. 未验证与风险

| 项 | 说明 | 验证方法 |
|---|---|---|
| M2 / 16 GB 上的加载时间与内存 | 上面的数据在 M3 Pro / 36 GB 取得 | 在基线机器上重跑 `ResidentMemoryProbe`，记录预热耗时与总驻留 |
| 16 GB 同时驻留语音 + 整理 + 翻译 | 仍是 S1 未决项；预热让三者更容易同时在内存里 | S1 联合实测；必要时唤起时只预热起始输出（已是这样），并缩短整理 / 翻译的空闲时间 |
| 唤起即听写（自动听写）时仍可能等一下 | 若语音刚被卸载（> 30 分钟未用），唤起时才加载，约 2–3 s | 状态行已提示；可调 `SpeechIdleTimeout` |
| Windows | 逻辑同一套，时间与内存未测 | Windows 实机 |
| 首次请求仍比后续慢（整理约 1.1 s vs 0.4 s） | llama 首次请求的一次性开销 | 若需要，预热时发一条极短请求（尚未做） |
